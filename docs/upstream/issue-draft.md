## 8. Внешняя проверка подхода (2026-10-22)

Проверено по сети, насколько форма «сначала issue с патчами, PR только по просьбе» соответствует
общепринятой практике.

**Подтверждается:**

- `opensource.guide / How to contribute`: для substantial contribution — «ask before working on it», новое предложение
  вносить «in an issue». Наш случай (+233 / −96 в базовом типе) — именно substantial, значит маршрут «сначала issue»
  нормативный, а не обходной.
- `awesome-maintainer-defense/policies/UNSOLICITED_PULL_REQUESTS.md`: «Before starting a large change, open or join an
  issue and wait for maintainer agreement on the problem and approach» и «Generating a patch locally does not
  authorize opening a pull request». Прямое подтверждение нашей позиции, включая вариант для агента.
- Там же предписанная структура короткого предложения: problem, intended scope, likely files, compatibility effects,
  verification approach. У текста issue это и есть `Summary` / `Key Changes` (по файлам) / «Стоимость для тебя» +
  статические проверки совместимости / `Verification`.
- CNCF и Kubernetes contributor docs называют «drive-by pull requests» отдельной проблемой, против которой
  работают через привязку к issue.
- **Прямой прецедент в нашей нише** — `minecraft-optimization-project/mcopt`: «Measured, upstream-first performance
  fixes for popular Minecraft mods». Их шаги: минимальный ревьюабельный коммит, before/after цифры в тексте,
  «Upstream first», «Respect licenses. We only redistribute modified builds where the license allows it», и для
  модов с запрещающей лицензией — companion-мод `mcopt-patches`, патчащий исходный jar **в рантайме**, вместо
  пересобранного дистрибутива. Это ровно наша связка «апстрим-запрос + локальный патчер, пересобранный ARR-jar
  никогда не публикуется», только в другом домене.

**Где норма расходится (наши отступления, и почему они осознанные):**

1. mcopt на шаге 5 делает **PR**, и штатный механизм GitHub — форк + PR: мейнтейнер мержит его в два клика, а
   `.patch` из issue надо применять руками. Мы идём через issue по двум конкретным причинам: у этого репо внешний PR
   не получает вообще никакой CI-проверки (`build.yml` без `pull_request`), и единственная наружная попытка (#30)
   стоит неткнутой, тогда как оба смерженных пришли из его собственной `claude/*`-среды; плюс публичный форк
   Tree с «Personal use only» перепубликует чужое дерево, а патч-файл — только наш дельта-код.
2. `opensource.guide` упоминает **draft PR** как признанный компромисс: diff виден, ревью не требуется. Это разумный
   второй шаг, и он уже предложен одной строкой в конце текста («если удобнее получить веткой или PR — скажи,
   оформлю») — но по первому разу мы его не открываем сами.
3. Гайд явно проговаривает **политику молчания**: ждать неделю+, затем один вежливый пинг, и если ответа нет —
   идти дальше, а не добиваться. У нас этого пункта не было: см. §6, п. 5.
4. Тот же гайд советует до вложения сил проверить активность репо и скорость ответов. Мы это измерили (коммиты
   ежедневно до 2026-10-20, issue закрываются в тот же день), и наш проект от merge не зависит — порт доделывается
   локально в любом случае, что снимает главный риск формы.
