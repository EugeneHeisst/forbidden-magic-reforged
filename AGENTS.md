# Forbidden Magic: Reforged

Порт аддона Forbidden Magic 0.574 (MC 1.7.10, SpitefulFox) на Thaumcraft 4: Reforged. Основной таргет
— MC 26.3, второй — MC 1.21.1 (ветка хоста `mc/1.21.1`), только после зелёного гейта на основном.
Логика, числа, рецепты, тексты и ассеты оригинала переносятся 1:1; технический слой пишется на
современных API. Спека и план в `docs/superpowers/`: в спеке измерения и обоснования, в плане
разбиение по задачам.

Это единственный источник правил: `CLAUDE.md` импортирует их через `@AGENTS.md`. Машинно-специфичное
(пути на этой машине, оболочка, что индексировано) живёт в `AGENTS.local.md` — он в git не идёт и
может отсутствовать; если файл есть, читай его вместе с этим.

  Локально, в git не идёт. Материал для сверки поведения; код оттуда не заимствуется.
- Четыре репозитория — соседи одного каталога: относительные `../` пути часть контракта. Если один из
  них переехал, `../` молча укажет в пустоту; проверь, что каталог оригинала непустой.

## Гейт: что считается сделанным

Срез не считается сделанным без свежего вывода команд.

- `cmd //c gradlew.bat build runGameTestServer` → `BUILD SUCCESSFUL` и `All N required tests passed`
  без пропусков. N меняется — не подставляй число в документы.
- Пропатченный хост: `python tools/prepare_host.py --verify` → `host matches sha + K patch commit(s)`.
- Восстановление после чистки: `prepare_host.py` → `cd host && cmd //c gradlew.bat publish` → сборка
  аддона (минута-две). Без `maven/` сборка падает на `thaumcraft:1.2`.
- Визуальное (модели предметов, рендер, creative-вкладка) headless-гейт не доказывает: нужен
  `runClient` со скриншотом окна. Запуск игры, визуальную проверку и партию двумя клиентами делает
  пользователь.

## Сверка с оригиналом

- Любая строка в `docs/fidelity.md` и любое «оригинал делал иначе» — утверждение, а не факт. Проверяй
  по исходникам `../ForbiddenMagic` до того, как что-то исправлять или закрывать.
- Сверяй то, где поведение действительно определено (точки вызова, рецепты, research), а не только
  аргументы конструкторов.
- Идиома 1.7.10 не является требованием: если в 26.x класса или поля оригинала нет, это другой идиом,
  а не регресс.

## Хост: пиним, не правим

- Хост пинится sha в `host.sha`, копия собирается в `host/` (в git не идёт), наши изменения живут
  только патчами в `patches/*.patch`. Рабочее дерево хоста только читаем: `git -C ../thaumcraft-4-reforged status --porcelain` должен оставаться пустым.
- В `host/` нельзя править руками и нельзя коммитить туда: `prepare_host.py` делает `checkout --force` + `clean -f -d` + `git am`, поэтому незакоммиченные правки обнуляются, а проверка
  «commits ahead == количество патчей» ломается. Цикл правильный: правь файл в `patches/`, потом
  запускай `prepare_host.py`.
- Пропатченная копия отчитывается версией ровно `1.2`. Не `1.1` и не `1.2-fm.1`: пре-релизный
  квалификатор сортится ниже `1.2`, и наш собственный `versionRange="[1.2,)"` тогда не разрешается.
- Ни один класс и ни один ассет хоста не попадает в наш jar. Проверяет `tools/check_provenance.py` в
  каждом гейте.

## Git и параллельные сессии

- Это не единственный редактор репозитория: другая сессия работает в том же дереве. Пиши и коммить в
  одном ходе; перед коммитом — `git log --oneline -1` и `git status`, чтобы не принять чужой коммит за
  свой и не потерять свои файлы.
- В `git add` только явные пути. `-A` и `commit -a` запрещены: чужие правки уедут под твой комментарий.
- `git push` и любое переписывание истории — только по явной просьбе. `main` не force-push.
- Сгенерированные файлы на Windows пишутся с CRLF и показываются как изменённые при идентичном
  содержимом: смотри diff с `--ignore-all-space` и не «чинить» переводы строк.

## Ресурсы, регистрация, стиль

- Ресурсы делают генераторы в `tools/`, исходные тексты и карты — в `data/` (`data/lang`,
  `data/id_map.json`); datagen не используется. Повторный прогон генератора не должен менять файлы.
- Новый предмет без записи в `tools/gen_resources.py` рендерится как `Missing item model`, даже когда
  все GameTest зелёные. Предмету нужны и `models/item/<id>.json`, и `items/<id>.json`.
- Конструктор регистрирует конфиг, регистраторы и `DeferredRegister`; сами аспекты создаются в
  `FMLCommonSetupEvent`, потому что `no_lust` — STARTUP-конфиг и должен быть прочитан до регистрации.
  Аспекты до таблицы меток, предметы до рецептов, проверка доступности API хоста до любого к нему
  обращения. `no_lust` гасит саму регистрацию `luxuria`, как `DarkAspects.java:28`; значения конфига на
  клиенте и сервере должны совпадать, иначе разойдутся ordinal-таблицы аспектов.
- Конфиги только `SYNCED` / `STARTUP` / `CLIENT`: `ModConfig.Type.COMMON` удалён в FML 12, на нём
  падает NeoForge 26.3.0.37+.
- Тесты — только GameTest.
- Java и Python: 4 пробела, без комментариев. Коммиты на английском, `feat:` / `fix:` / `docs:` /
  `chore:`, без строк соавторства. Языки только `en_us` и `ru_ru`, формулировки оригинала сохраняются.

## Отступления от оригинала

Единственный список отличий — `docs/fidelity.md`; не заводить второй. Здесь только правила, которые
иначе будут выведены заново.

- Баги оригинала чиним только если они ломают игру: дюп, потеря предметов, NPE, рассинхрон, краш
  сервера.
- Любое другое расхождение попадает в `docs/fidelity.md`, а не устраняется молча.
- Жёсткий список заражающих блоков у хоста — единственное внешнее ограничение проекта. Остальные
  отличия — выбор, а не потолок платформы: 26.x умеет и оригинальное поведение.
